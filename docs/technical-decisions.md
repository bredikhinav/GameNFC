# ФантикПэй — технические решения

Дополняет [architecture.md](architecture.md) — исходную архитектуру продукта. Здесь описано, как она реализована и где реализация отличается.

## Стек

| Слой | Решение |
| --- | --- |
| Сервер | Python 3.11, FastAPI, SQLAlchemy 2 (async) + asyncpg, Alembic, Pydantic 2 |
| Хранилище | PostgreSQL 16 — данные, Redis 7 — ограничение частоты запросов |
| Приложение | Flutter (Android + iOS), Riverpod, go_router, drift (SQLite), dio, nfc_manager 4 |
| Инфраструктура | Docker Compose на одном VPS: API, задания по расписанию, PostgreSQL, Redis, Caddy (HTTPS), ежедневный бэкап |
| CI | GitHub Actions: ruff + pytest для сервера; analyze + тесты приложения против поднятого API |

Домен — `fantikpay.ru`. Название приложения — «ФантикПэй», ID пакета — `ru.fantikpay.app`.

## Журнал операций

- Каждая операция — одна строка `transactions`: `from_wallet_id → to_wallet_id`, `amount > 0`. Это и есть двойная запись: у каждого движения есть источник и получатель. Отдельная таблица проводок не нужна.
- Системные кошельки пространства `bank` и `shop` — контрагенты начислений и списаний, поэтому **сумма всех кошельков пространства всегда равна нулю**. Банк уходит в минус — он эмитент.
- `wallets.balance` — кэш. Команда `python -m app.cli reconcile` каждую ночь пересчитывает балансы из журнала и проверяет нулевую сумму.
- Ошибка исправляется только операцией `reversal` (`reverses_id` уникален — дважды отменить нельзя). Задним числом можно поменять только комментарий (`POST /transactions/{id}/comment`), суммы — никогда.

### Конкурентность и порядок

Каждая запись в пространстве начинается с `UPDATE spaces SET seq = seq + 1 RETURNING seq`. Это решает две задачи сразу:

1. Блокировка строки пространства держится до коммита, поэтому записи внутри одного пространства выполняются последовательно — двойное списание невозможно. Кошельки дополнительно блокируются `SELECT … FOR UPDATE`. Тест: 25 параллельных списаний по 100 при балансе 1000 — проходят ровно 10.
2. Каждой изменённой строке ставится `seq`, и порядок `seq` совпадает с порядком коммитов. Поэтому курсор синхронизации «всё, где `seq > cursor`» ничего не пропускает.

Нагрузка из требований (20 терминалов на пространство) — это десятки записей в секунду в пике, для последовательной записи с короткими транзакциями это немного.

### ID от клиента

Телефон сам генерирует UUID операций, игровых сессий и заявок. Повторная отправка возвращает исходный результат (`duplicate: true`), а тот же id с другим типом возвращает `id_conflict`. ID кошельков детерминированы (UUIDv5 от id игрока и сессии), поэтому телефон без сети создаёт кошелёк игры с тем же id, который потом создаст сервер. Совпадение проверяется тестом в `app/test/core_test.dart`.

## Офлайн и синхронизация

- Приложение хранит копию пространства в SQLite: игроки, карты, кошельки (баланс по данным сервера), сессии, участники, операции и шаблоны.
- **Отображаемый баланс = баланс сервера + неподтверждённые локальные операции.** Поэтому после синхронизации не нужно ничего пересчитывать: подтверждённые операции приходят с сервера, а локальные копии помечаются как отправленные.
- Любое действие ведущего (операция, создание игры, вход игрока, пауза, завершение) сразу применяется локально и ставится в очередь `outbox`. Очередь отправляется `POST /sync` сразу после операции, при появлении сети, при возврате в приложение и раз в 30 секунд, пока в ней что-то есть.
- `POST /sync` применяет операции по порядку, каждую в своей транзакции БД: одна отклонённая не блокирует остальные. Потом сервер отдаёт изменения после курсора, страницами по 2000 значений `seq`.
- Операции, которые уже произошли офлайн, сервер принимает, даже если они уводят в минус: монеты уже потрачены в реальной жизни. Такой кошелёк помечается `flagged`, администратор снимает пометку. Онлайн-проверки (`POST /transactions`, детские переводы) строгие.
- Операция по карте, заблокированной позже, чем операция прошла офлайн, остаётся в силе.
- Лимит офлайн-трат (`offline_spend_limit`, по умолчанию 50 для организаций) проверяет телефон, когда нет сети.
- Отмена на экране результата: если операция ещё в очереди, она просто удаляется. Если уже на сервере — создаётся `reversal`.

## Карты

- На карте только NDEF-ссылка `https://fantikpay.ru/c/<token>`: 16 символов base62, около 95 бит. Если NDEF не читается, карта находится по UID чипа.
- Страница `/c/<token>` ничего не говорит о владельце: карту может найти посторонний.
- При активации запоминается UID. Если ссылку скопировали на другой чип, активация вернёт `card_uid_mismatch`. Полную защиту от клонирования даст только NTAG424 DNA (фаза 4).
- Статусы: `in_stock → active → blocked / unlinked`. Заблокированная карта сохраняет игрока, чтобы офлайн-операции, сделанные до блокировки, остались в силе.

### Как попадают карты в базу

1. **MVP, пустые NTAG215.** Родитель нажимает «Привязать карту» и прикладывает пустую карту. Приложение запрашивает `POST /cards/prepare`, записывает ссылку на карту и активирует её. Блокировка от перезаписи в MVP не включена.
2. **Складские партии.** Команда `python -m app.cli generate-batch --name "Партия 1" --count 500 --chip ntag215 --out batch.csv` создаёт карты в статусе `in_stock` с кодами активации. CSV отдаётся производителю для записи и печати кодов на упаковке. Если производитель сам выдаёт токены и UID, используйте `import-batch`. Приложение распознаёт карту со ссылкой и при активации просит код с упаковки. Отдельное устройство не нужно.
3. **Своя запись партиями** — USB-считыватель ACR122U/ACR1252U и скрипт на ноутбуке (пока не сделано).

## Безопасность

- Пароли — Argon2. Access JWT живёт 15 минут. Refresh-токен ротируется, а повторное использование старого токена разлогинивает все сессии пользователя.
- Телефон ребёнка получает отдельный токен `fpd_…` (в базе хранится хэш), родитель может его отозвать. Детский токен не подходит к API взрослых, и наоборот.
- PIN терминала — 4 цифры, PBKDF2-SHA256 с 120 000 итераций. Хэш получает только устройство самого пользователя, поэтому PIN работает без сети. После каждых 5 ошибок — пауза 30 секунд.
- Ограничение частоты запросов в Redis: вход, регистрация, восстановление пароля, привязка QR, неизвестные карты на терминале.
- В проде сервер не стартует с секретом JWT по умолчанию.

## Персональные данные детей

Хранятся только прозвище, аватар из набора и (необязательно) год рождения и отряд. При создании профиля фиксируется, кто дал согласие и когда (`consent_user_id`, `consent_at`). Удаление профиля обезличивает запись: имя стирается, карты отвязываются, телефоны отзываются, а журнал операций остаётся без персональных данных.

## Детский режим

Работает только онлайн, а офлайн показывает последний сохранённый `/me` с пометкой «Обновлено N минут назад». Переводы идут через `POST /me/transfers` с проверкой дневного лимита. Перевод больше порога становится заявкой, её одобряет родитель. В лагере список «Кому» ограничен отрядом ребёнка, остальным можно перевести по карте.
